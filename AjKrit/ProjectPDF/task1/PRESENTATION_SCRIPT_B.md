# สคริปต์นำเสนอ Task 1 — Knowledge Graph ชุด B

## 1. บทนำ

สวัสดีครับ วันนี้ผมจะนำเสนอ Project 2 งานที่ 1 เรื่องการสร้าง Knowledge Graph จากไฟล์ PDF และจัดเก็บใน Neo4j ครับ

ปัญหาของข้อมูลใน PDF คือ เนื้อหาอยู่ในรูปข้อความต่อเนื่อง ถึงแม้คนจะอ่านได้ แต่ระบบยังไม่เข้าใจว่าอะไรคือหัวข้อ อะไรคือเอกสาร หลักฐาน หน่วยงาน หรือช่องทางติดต่อ และข้อมูลเหล่านี้สัมพันธ์กันอย่างไร

เป้าหมายของงานนี้จึงเป็นการเปลี่ยนข้อมูลจาก PDF ให้เป็นโครงสร้าง Node และ Relationship เพื่อให้สามารถดูความเชื่อมโยงและใช้ Cypher Query ค้นหาข้อมูลสำคัญได้ครับ

## 2. ข้อมูลที่ใช้

ข้อมูลต้นทางคือไฟล์ “คู่มือประชาชน สำนักงานตำรวจแห่งชาติ” ผมเลือก PDF หน้าไฟล์ 21 ถึง 30 ซึ่งตรงกับเลขหน้าพิมพ์ 8 ถึง 17 รวมทั้งหมด 10 หน้า

ขอบเขตข้อมูลคือหมวด 1 “คำแนะนำในการไปติดต่อที่สถานีตำรวจ” และหัวข้อย่อยตั้งแต่ 1.1 ถึง 1.16 เช่น การเตรียมเอกสาร การแจ้งเอกสารหาย การแจ้งคนหาย การแจ้งรถหาย และการแจ้งเช็คไม่มีเงินครับ

## 3. โมเดลที่ใช้

ระบบนี้ใช้ Embedding Model คือ `intfloat/multilingual-e5-large` ซึ่งรองรับหลายภาษาและใช้วิเคราะห์ความใกล้เคียงทางความหมายของข้อความภาษาไทย

ส่วน LLM ใช้ `Qwen3.8-27B` แบบ GGUF quantization ระดับ Q4 โดยดาวน์โหลดและรันภายในเครื่องผ่าน Ollama ไม่ได้ส่งข้อมูลไปยัง LLM API ภายนอก

Embedding ช่วยวิเคราะห์ความหมายและเสนอประเภทของข้อมูล ส่วน LLM ช่วยสกัด Entity, Relationship, Owner, Condition และข้อความหลักฐานจาก PDF ครับ

## 4. กระบวนการทำงาน

กระบวนการเริ่มจากดึงข้อความออกจาก PDF และเก็บเลขหน้าไว้เป็น provenance จากนั้นแบ่งข้อความตามหัวข้อ 1.1 ถึง 1.16 เพื่อไม่ให้บริบทของแต่ละหัวข้อปะปนกัน

ข้อความของแต่ละหัวข้อถูกส่งเข้า multilingual-e5-large เพื่อสร้าง semantic embedding และช่วยจับความหมายของคำที่เกี่ยวข้องกัน ต่อจากนั้น Qwen ใช้ข้อมูลพร้อม ontology ที่กำหนดไว้ เพื่อสกัด Entity และ Relationship ออกมาเป็นข้อมูลแบบ JSON

ก่อนนำเข้า Neo4j ระบบตรวจ schema, ทิศทางของความสัมพันธ์, Entity ซ้ำ, ข้อความ evidence และเลขหน้า PDF อีกครั้ง ข้อมูลที่โมเดลตกหล่นหรือแบ่งประเภทไม่เหมาะสมจะถูกแก้โดยตรวจเทียบกับต้นฉบับ

ดังนั้น LLM ทำหน้าที่ช่วยสกัดข้อมูล แต่ข้อเท็จจริงในกราฟสุดท้ายต้องมีข้อความจาก PDF รองรับครับ

## 5. การออกแบบ Ontology

[เปิดภาพรวมกราฟ B]

โครงสร้างระดับบนเริ่มจาก `SourceDocument` ซึ่งแทนไฟล์คู่มือ จากนั้นเชื่อมด้วย `HAS_CHAPTER` ไปยัง `Chapter` ชื่อ “1. คำแนะนำในการไปติดต่อที่สถานีตำรวจ”

Chapter เชื่อมด้วย `HAS_SECTION` ไปยัง `Case` ครบตั้งแต่หัวข้อ 1.1 ถึง 1.16

แต่ละ Case สามารถเชื่อมไปยัง Entity ประเภทต่าง ๆ ได้แก่ `Document`, `Evidence`, `Organization`, `PersonRole` และ `Contact`

ตัวอย่าง Relationship ที่ใช้คือ `HAS_SUPPORTING_EVIDENCE`, `HANDLED_BY`, `NOT_HANDLED_BY`, `CERTIFIED_BY`, `CONTACT_ORGANIZATION` และ `HAS_CONTACT`

การแยก Relationship ตามความหมายช่วยให้เราแยกได้ว่า Entity ใดเป็นเอกสารประกอบ Entity ใดเป็นหน่วยงานรับดำเนินการ และ Entity ใดเป็นข้อยกเว้นครับ

## 6. ผลลัพธ์ของกราฟ

กราฟชุด B หลังตรวจเทียบกับต้นฉบับมีทั้งหมด 81 Nodes และ 99 Relationships และเชื่อมเป็น component เดียว

81 Nodes ประกอบด้วย SourceDocument 1, Chapter 1, Case 16, Document 34, Evidence 17, Contact 3, Organization 5 และ PersonRole 4 Nodes

99 Relationships แบ่งเป็นความสัมพันธ์จากเนื้อหา 82 เส้น และความสัมพันธ์โครงสร้าง 17 เส้น ซึ่งประกอบด้วย `HAS_CHAPTER` 1 เส้น และ `HAS_SECTION` 16 เส้น

ก่อน source review โมเดลชุด B เสนอ Candidate Relationships 67 รายการ และมี 58 รายการที่ตรงกับความสัมพันธ์เนื้อหาสุดท้าย 82 เส้น คิดเป็นความครอบคลุมประมาณ 70.7 เปอร์เซ็นต์ ส่วนที่เหลือได้รับการเติมหรือแก้จากข้อความต้นฉบับก่อนนำเข้า Neo4j ครับ

## 7. ตัวอย่าง Cypher Query

[เปิดกราฟรายละเอียดหัวข้อ 1.4]

ตัวอย่างคำถามคือ “หากต้องการแจ้งความคนหาย ต้องเตรียมหลักฐานอะไร และสามารถติดต่อหน่วยงานหรือเบอร์โทรใดได้บ้าง”

ผมใช้ Cypher เลือก Case หมายเลข 1.4 แล้วดึง Entity ที่เชื่อมต่อ รวมถึงค้นหาความสัมพันธ์ต่อจาก Organization ไปยัง Contact

ผลลัพธ์แสดงว่า หัวข้อแจ้งความคนหายเชื่อมกับบัตรประจำตัวผู้หาย สำเนาทะเบียนบ้าน ภาพถ่าย สูติบัตร และใบสำคัญทหาร นอกจากนี้ยังเชื่อมกับ Organization “ศูนย์ข้อมูลคนหาย มูลนิธิกระจกเงา” และเชื่อมต่อไปยังเบอร์โทร 0807752673

จุดนี้แสดงข้อดีของ Knowledge Graph เพราะไม่ได้ค้นพบเพียงข้อความที่มีคำเหมือนกัน แต่สามารถเดินตามความสัมพันธ์จาก Case ไปยัง Organization และ Contact ได้ครับ

## 8. ตัวอย่างข้อยกเว้น

[เปิดกราฟหัวข้อ 1.2]

อีกตัวอย่างคือคำถามว่า “กรณีบัตรประชาชนหาย ต้องติดต่อใคร ใครรับรองได้ และต้องแจ้งตำรวจหรือไม่”

หัวข้อนี้แสดง Relationship หลายประเภท เช่น `HANDLED_BY` สำหรับสำนักงานทะเบียน, `CERTIFIED_BY` สำหรับบุคคลที่รับรองได้ และ `NOT_HANDLED_BY` ซึ่งแสดงข้อยกเว้นว่าตามข้อความในคู่มือ กรณีทำบัตรใหม่ไม่ต้องแจ้งความต่อเจ้าหน้าที่ตำรวจ

ตัวอย่างนี้แสดงว่าทิศทางและชื่อของ Relationship มีความหมายต่อการตอบคำถาม ไม่ได้เป็นเพียงเส้นเชื่อมระหว่าง Node ครับ

## 9. การตรวจสอบคุณภาพ

ผมตรวจสอบว่า Node ID และความสัมพันธ์ไม่ซ้ำ ไม่มี Relationship เชื่อมข้ามชุดข้อมูล ทุกเส้นเนื้อหามี evidence และเลขหน้า PDF และทุก Node สามารถเดินกลับไปยัง SourceDocument ได้

Cypher สำหรับแสดงผลและตรวจคุณภาพรันสำเร็จทั้งหมด และชุดทดสอบของระบบผ่าน 26 Tests ครับ

## 10. สรุป

งานนี้แสดงกระบวนการเปลี่ยนข้อมูลภาษาไทยจาก PDF ให้เป็น Knowledge Graph โดยใช้ multilingual-e5-large วิเคราะห์ความหมาย ใช้ Qwen3.8-27B ช่วยสกัดข้อมูล ใช้ ontology ควบคุมประเภท Entity และ Relationship จากนั้นตรวจหลักฐานก่อนนำเข้า Neo4j

ผลลัพธ์คือกราฟ 81 Nodes และ 99 Relationships ซึ่งสามารถแสดงโครงสร้างของคู่มือและใช้ Cypher ตอบคำถามจากสถานการณ์จริงได้อย่างชัดเจน

จบการนำเสนอ ขอบคุณครับ

## คำตอบสำรองกรณีอาจารย์ถาม

**ทำไมเลือก multilingual-e5-large?**

เพราะรองรับข้อความหลายภาษา รวมถึงภาษาไทย และในการทดลองของงานนี้ให้ Candidate ที่ตรงกับความสัมพันธ์หลังตรวจต้นฉบับมากกว่าทางเลือกที่ทดลองอีกชุดเล็กน้อย จึงเลือกเป็นโมเดลหลักสำหรับนำเสนอ

**LLM สร้างกราฟครบ 99 เส้นเองหรือไม่?**

ไม่ครับ LLM ช่วยเสนอ Candidate Relationships ส่วนกราฟสุดท้ายผ่าน schema validation, duplicate checking และ source review กับข้อความ PDF จึงไม่อ้างว่า 99 เส้นเป็นผลลัพธ์ดิบจาก LLM ทั้งหมด

**ทำไมต้องใช้ Embedding และ LLM ร่วมกัน?**

Embedding เหมาะกับการวัดความใกล้เคียงทางความหมาย ส่วน LLM เหมาะกับการอ่านข้อความแล้วสกัด Entity, Relationship และเงื่อนไข การใช้ร่วมกันจึงช่วยทั้งด้าน semantic matching และ structured extraction ครับ
