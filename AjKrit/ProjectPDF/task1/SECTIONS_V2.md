# Pipeline รอบปรับปรุง: สกัดทีละหัวข้อ

ใช้ PDF หน้า 21–30 หัวข้อ 1.1–1.16 เช่นเดิม แต่รวมข้อความแต่ละหัวข้อข้ามหน้าแล้วก่อนส่ง LLM ผลรอบนี้แยกไว้ใน `artifacts/sections_v2` ไม่เขียนทับผล A/B เดิมหรือกราฟตรวจด้วยมือ

A = BGE-M3, B = multilingual-e5-large ทั้งคู่ใช้ Qwen3.8-27B GGUF UD-Q4_K_M และกติกาเดียวกัน ใช้ cache embedding ที่คำนวณจริงจาก 10 หน้าเดิม แล้วรวม ontology hints ของหน้าที่หัวข้อนั้นครอบคลุมด้วยค่าสูงสุด ไม่ได้อ้างว่าเป็น section embeddings ที่คำนวณใหม่

## สิ่งที่เปลี่ยน

- แก้ชื่อหัวข้อขึ้นบรรทัดใหม่และรวมบริบทข้ามหน้า โดยเก็บ mapping ถึงเลขหน้าเดิม
- เพิ่มความหมายเส้นครบ 7 ประเภท รวม CERTIFIED_BY, ISSUES, ABOUT_DOCUMENT
- ให้ LLM ระบุ owner/condition และเลขบรรทัดเริ่ม–จบ โปรแกรมดึงข้อความ evidence จริงให้ ไม่ให้โมเดลพิมพ์หลักฐานยาวจน OCR ตัวอักษรเพี้ยน
- รวมคำพ้องตามพจนานุกรมประกาศ เช่น ใบเกิด→สูติบัตร และรูปถ่าย→ภาพถ่าย การรวมชื่อเอกสารที่มีเจ้าของต้องมี owner ก่อน
- ตรวจประเภทปลายทางตาม relation ไม่ยอมให้ PersonRole เป็น HAS_SUPPORTING_EVIDENCE ไม่ยอมรับเบอร์ที่ไม่ใช่เลขโทรศัพท์ และโหนดชื่อ “สำเนา” ที่ไม่บอกว่าอะไร
- ชื่อที่รวมหลายรายการและเงื่อนไขที่อาจตกหล่นเข้า review queue; ไม่อ้างว่าตรวจความหมายได้อัตโนมัติทั้งหมด
- Stable IDs ป้องกันข้อมูลซ้ำ เก็บ raw response, fingerprint, rejected, aliases, evidence spans และสถานะตรวจแยกจากกัน

ไม่ได้ใช้รายการคำตอบจาก reference_inventory ป้อนให้ LLM หรือเติมข้อเท็จจริงเพื่อให้ผลคะแนนดีขึ้น

## รันและติดตาม

จาก `Project2/task1`:

```bash
.venv/bin/python -m unittest discover -p 'test*.py'
.venv/bin/python section_pipeline.py --import-neo4j > artifacts/sections_v2/run.log 2>&1
```

อย่ารันคำสั่งซ้ำระหว่างโปรเซสเดิมทำงาน Resume จะข้ามหัวข้อที่เสร็จและ fingerprint ตรง แต่ละกลุ่มมี 16 requests แบบ sequential โปรแกรมบันทึก `progress.json` ระหว่างสร้างคำตอบ ถ้าตอบเสีย/ถูกตัดจะ retry หนึ่งครั้งก่อนหยุดพร้อมไฟล์ error

รอบ A/B เดิมใช้รวมประมาณ 64 นาทีเฉพาะ LLM รอบใหม่ประเมินเบื้องต้น 1–2 ชั่วโมง แต่ขึ้นกับจำนวนคำตอบ การโหลดโมเดล ความเร็ว GPU/RAM และงานร่วมบนเครื่อง ยังไม่ใช่เวลาเสร็จที่รับรอง

นำเข้าเมื่อกลุ่มนั้นครบเท่านั้น โดยใช้ `SectionKG` + `group` เพื่อแยกจาก Semantic10 รุ่นเดิมและ Task1Reviewed

```cypher
MATCH (c:SectionKG:Case {group:'B'})-[r]->(e:SectionKG {group:'B'})
RETURN c,r,e;
```

เปลี่ยน B เป็น A เพื่อดูอีกชุด สีใน Browser ต้องให้ Case/Document/Evidence ฯลฯ อยู่ก่อน label ร่วม SectionKG ใน Update styling priority

หลังรัน ตรวจโครงสร้างและสร้างตาราง review:

```bash
.venv/bin/python validate_sections.py
```

## การพิสูจน์ตามเกณฑ์

| เกณฑ์ | สิ่งที่ใช้พิสูจน์ | สิ่งที่ต้องตรวจหลังรัน |
|---|---|---|
| Graph structure | schema, relation endpoint whitelist, owner/condition/provenance | ไม่ให้ประเภทเอกสารกับวัตถุจริงปะปน |
| Nodes | หัวข้อจากต้นฉบับและ entity จาก LLM | ตัว Case สร้างจากหัวข้อครบ 16 ไม่ได้หมายความว่าโมเดลสกัดครบ ต้องดูหัวข้อที่มีเส้นและรายการตกหล่น |
| Relationships | ทิศทาง Case→ประเภทปลายทาง, line evidence | ความหมายจริง ตัวเลือก/ข้อยกเว้น และความครบ |
| ความถูกต้อง/ไม่ซ้ำ | ID, dedup, source spans, aliases, review.csv | ทุกแถว flagged และ rejected รวมทั้ง semantic omissions |
| Cypher/แสดงผล | queries และผลนำเข้าจริง | ภาพรวม/กราฟย่อยต้องอ่านชื่อและเส้นได้ |

ยังรับรอง 2 คะแนนทุกข้อไม่ได้จาก tests อย่างเดียว ต้องตรวจข้อมูลที่สกัดจริงเทียบต้นฉบับก่อน ข้อมูลชุดนี้สะท้อนคู่มือฉบับที่ได้รับ ไม่ได้ปรับข้อกฎหมายให้เป็นปัจจุบัน

## การตรวจหลังรันที่ตั้งไว้

เมื่อทั้งสองชุดครบ จะ revalidate จาก raw response ด้วยกฎแก้เลขบรรทัดที่พบชื่อ/alias ตรงตัวเพียงตำแหน่งเดียวและอยู่ห่างไม่เกิน 2 บรรทัด เก็บช่วงเดิมและช่วงแก้เพื่อ audit ไม่แก้ชื่อโดยเดา จากนั้นสร้าง validation.json/review.csv และนำเข้า Neo4j พร้อมทดสอบนำเข้าซ้ำ จำนวนต้องไม่เพิ่ม ดู finalization-status.json และ finalization.log

คำ owner ที่ไม่พบตรงตัวในหัวข้อจะถูก flag ให้ตรวจความหมาย ไม่ได้ถือว่าถูกเพียงเพราะ entity มีหลักฐาน การตรวจอัตโนมัติครบยังไม่ใช่ semantic review ครบ
