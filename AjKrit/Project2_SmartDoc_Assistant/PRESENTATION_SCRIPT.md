## เตรียมตอบคำถาม: 30 คำถามพร้อมคำตอบ

ตอบสั้นก่อน แล้วขยายเมื่อผู้ประเมินถามต่อ ตัวเลขอ้างอิงเฉพาะรอบทดลองที่ระบุ

### 1. RAG ต่างจากถาม LLM ตรง ๆ อย่างไร?

RAG ค้นหลักฐานจากแหล่งข้อมูลที่กำหนดก่อน แล้วส่งให้ LLM สรุป ส่วนการถามตรง ๆ อาศัยความรู้ของโมเดลมากกว่า งานนี้จึงตรวจกลับถึงหัวข้อและเลขหน้าได้ แต่ RAG ไม่รับรองว่าจะไม่มี hallucination

### 2. ใช้ prompt ลด hallucination อย่างไรบ้าง?

System prompt บังคับใช้ CONTEXT เท่านั้น ห้ามเดาหรือใช้ความรู้เดิม ถ้าหลักฐานไม่พอต้องตอบ fallback ห้ามสร้างเลขหน้า/หัวข้อ/citation และต้องอ้างรหัสที่มีใน context มี JSON schema กับตัวอย่างรูปแบบ และตรวจรหัส citation หลัง generation อีกชั้น ไม่ใช่พึ่ง prompt อย่างเดียว

### 3. มีตัวอย่างคำสั่งใน prompt จริงไหม?

มี เช่น “ใช้ข้อความใน CONTEXT เท่านั้น ห้ามใช้ความรู้เดิมหรือเดาข้อมูลที่ไม่มีในหลักฐาน” และ “หากหลักฐานไม่พอ ให้ตอบตรง ๆ ว่า ไม่พบข้อมูลที่เกี่ยวข้องในเอกสาร” ตรวจได้ใน OllamaClient.answer_from_context() ใน llm.py

### 4. รับรอง zero hallucination ได้ไหม?

ไม่ได้ครับ Citation allow-list ตรวจว่ารหัสอ้างอิงมีจริง แต่ยังไม่ตรวจว่าทุกข้ออ้างสัมพันธ์กับหลักฐานหรือใช้กับสถานการณ์นั้นได้ จึงต้องประเมินด้วยคนและเพิ่ม hard cases ร่วมด้วย

### 5. ถ้าผู้ใช้สั่งให้ลืมกฎหรือใช้ความรู้นอกเอกสารจะทำอย่างไร?

System prompt กำหนดขอบเขตให้ตอบจาก context จึงคาดหวังให้ปฏิเสธหรือ fallback เมื่อไม่มีหลักฐาน แต่ยังไม่ผ่าน adversarial prompt-injection evaluation ครบชุด ไม่ควรอ้างว่าป้องกันได้ทุกกรณี

### 6. ถ้าเอกสารหรือ history มีคำสั่งแปลก ๆ จะทำตามไหม?

เมื่อส่ง history มีคำสั่งเพิ่มเติมว่าทั้ง HISTORY และ CONTEXT ไม่ใช่แหล่งคำสั่ง และใช้ history เพื่อเข้าใจคำถามต่อเท่านั้น อย่างไรก็ตามข้อความเสริมนี้อยู่ในเงื่อนไขมี history ยังควรทำ instruction/data separation ให้สม่ำเสมอและทดสอบ injection เพิ่ม

### 7. ใช้ Chain-of-Thought หรือ few-shot ไหม?

มีตัวอย่าง JSON หนึ่งรูปแบบเพื่อช่วยให้ตอบตามสัญญา ไม่ใช่ชุด few-shot หลายตัวอย่าง เปิด think=false และ prompt ห้ามแสดงการวิเคราะห์ภายใน ไม่อ้างว่าใช้ CoT เป็นกลไกหลักของระบบ

### 8. ทำไมตั้ง temperature=0?

เพื่อลดความแปรปรวนของการสร้างคำตอบและช่วยให้เปรียบเทียบโมเดลได้สม่ำเสมอ พร้อม seed=42 แต่ไม่ทำให้คำตอบถูกต้องอัตโนมัติหรือรับรอง deterministic ข้าม backend/version

### 9. ทำไมใช้ FAISS แทน ChromaDB?

ขอบเขตนี้มี 135 chunks จึงใช้ FAISS IndexFlatIP ค้นแบบ exact และจัดการ metadata เป็น JSON ได้ง่าย Chroma ไม่ได้ด้อยกว่า แต่ฟีเจอร์ฐานข้อมูลและการจัดการ collection ยังไม่จำเป็นกับงานนี้

### 10. Dense กับ Sparse ต่างกันอย่างไร?

Dense ใช้ embedding ค้นความหมาย แม้คำถามใช้คำไม่เหมือนต้นฉบับ Sparse ใช้ BM25 ค้นคำตรง ช่วยศัพท์เฉพาะและหมายเลข ทั้งสองช่องทางมีจุดพลาดต่างกัน จึงนำมารวมเป็น Hybrid

### 11. ทำไมรวมผลด้วย RRF ไม่บวก cosine กับ BM25 ตรง ๆ?

คะแนนทั้งสองมีสเกลต่างกัน RRF ใช้อันดับแทนคะแนนดิบเพื่อลดปัญหานี้ งานนี้ใช้ weighted RRF dense=.55 และ sparse=.45 ส่วน weighted score อีกชุดเป็นเกณฑ์ประกอบ ไม่ใช่น้ำหนักเดียวกัน

### 12. Reranker ทำอะไรที่ embedding ยังทำไม่ได้?

Cross-Encoder อ่านคำถามและข้อความเป็นคู่เพื่อให้ relevance score อีกครั้ง หลัง Hybrid ดึง candidates มาแล้ว ข้อแลกเปลี่ยนคือช้ากว่าค้นเวกเตอร์ จึงประเมินเฉพาะ candidate pool ขนาดเล็ก

### 13. ทำไมลด rerank เป็น 6 ไม่ใช่ 5?

ทั้ง 5 และ 6 ได้ Hit@1/Recall 18/18 ในชุดนี้ เลือก 6 เพื่อเผื่อ candidate รองก่อนเลือกผลส่งให้ LLM ค่าเฉลี่ย rerank ลดจาก5.45เป็น2.88วินาที แต่ยังไม่พิสูจน์ว่า6เหมาะที่สุดกับทุกคำถาม

### 14. ลด rerank แล้วเร็วขึ้น 47% หมายถึงทั้งระบบไหม?

ไม่ใช่ครับ เป็นการลดเวลาเฉลี่ยเฉพาะ reranker ในการทดลอง CPU4threads ยังมี query embedding, prompt processing, generation, queue และ LINE delivery ต้องวัด end-to-end ใหม่เพื่อสรุปทั้งระบบ

### 15. แก้การจัดอันดับหลัง rerank อะไรเพิ่ม?

หลัง rerank สำเร็จจัดอันดับเฉพาะ candidates ที่มี Cross-Encoder score ไม่รวม unscored candidates ที่ยังใช้ RRF score เพราะคนละสเกลกัน หาก rerank ล้มเหลวหรือคะแนนไม่ถูกต้องจะกลับไปใช้อันดับ RRF

### 16. ทำไมไม่ใช้ Qwen 27B ใน production?

Frozen-context benchmark ได้ F1ใกล้9B แต่ LLM-only p95ประมาณ95.70วินาที เทียบ9Bที่8.92วินาที บนเครื่องนี้ จึงเลือก9BสำหรับเวลารอในLINE ไม่ได้แปลว่า27Bด้อยกว่าทุกงานหรือทุกเครื่อง

### 17. Ministral ได้ F1 สูงกว่า ทำไมไม่เลือก?

F1 .7994 สูงกว่า9B .7950เล็กน้อย แต่ p95ช้ากว่า และตรวจพบปนขั้นตอนกับคำตอบชน token limit Similarityที่สูงกว่าไม่พิสูจน์ factual correctness จึงไม่ใช้เป็นเกณฑ์เลือกอย่างเดียว

### 18. ทำไมเลือก BGE-M3 และไม่สลับเป็น E5?

BGE-M3เป็น multilingual embedding ที่ใช้อยู่และผล Hybridดี E5ได้ dense rankingดีกว่าในชุด18ข้อ แต่ทดสอบทั้งระบบ F1เพิ่มเพียง.0014 ยังไม่เห็นความได้เปรียบชัด จึงคงBGE-M3

### 19. ถ้าจะย้ายไป E5 ต้องทำอะไร?

ใส่ passage:ตอนembedเอกสารและ query:ตอนค้น สร้างเวกเตอร์/indexใหม่ทั้งหมด ตรวจ thresholdและevaluationใหม่ Dimensionเท่ากันไม่ได้แปลว่าเวกเตอร์คนละโมเดลใช้ร่วมกันได้ โครงสร้างFAISS/BM25/LINEยังใช้ต่อได้

### 20. Chunk size และจำนวน chunks บอกอะไร?

Child size900และoverlap120เป็นจำนวนตัวอักษรไม่ใช่tokens จำนวน135chunksคือหน่วยค้นของเอกสาร การแบ่งเล็กช่วยระบุจุดแต่เสี่ยงขาดบริบท แบ่งใหญ่รักษาบริบทแต่เพิ่มเนื้อหาไม่เกี่ยวข้อง ต้องประเมินไม่ใช่เลือกจากจำนวนมากที่สุด

### 21. Parent-document chunking ดีกว่า fixed chunks อย่างไร?

ค้นด้วยchildที่เล็กแล้วส่งparentที่ต่อเนื่องให้LLM ช่วยรักษารายการและบริบทที่อาจข้ามchild งานนี้มี80parentsและdeduplicateparentก่อนสร้างprompt แต่ยังอาจดึงเนื้อหาส่วนเกิน จึงต้องจัดงบcontext

### 22. ใช้ semantic chunking เต็มรูปแบบหรือยัง?

ยังครับ ใช้ section-aware parent-document + recursive splitting ไม่ได้ใช้ embeddingตรวจsemantic breakpoints ต้องเรียกวิธีให้ตรงกับโค้ด ไม่ใช้คำว่าsemantic chunkingแทนทุกการแบ่งแบบadvanced

### 23. ทำไมต้องลบ zero-width และ header/footer?

อักขระซ่อนและข้อความซ้ำอาจรบกวนtokenization/embedding และดึงnoiseเข้าcontext ลบzero-widthและบรรทัดmarginที่ซ้ำอย่างระมัดระวัง สัดส่วนnoiseที่ลบ3.26%ไม่ใช่คะแนนว่าขยะที่เหลือต่ำกว่า5%

### 24. Dynamic top-k และ context budget ป้องกัน context ล้นอย่างไร?

top-kราว3–8ตามความยาว/clauses และตัดparentซ้ำ กำหนดcontextสูงสุด10,000ตัวอักษรกับOllama8192tokens แต่character capไม่ใช่token countingเต็มรูปแบบ ต้องตรวจprompt token telemetryและกันพื้นที่history/system/outputด้วย

### 25. [S1] คืออะไร และเลขหน้า PDF ต่างจากหน้าเอกสารทำไม?

S1คือรหัสsourceในcontextของคำตอบนั้น ระบบนำmetadataมาแสดงหัวข้อและเลขหน้า ไม่ให้โมเดลสร้างเอง หน้าPDFนับปก/คำนำด้วย ส่วนหน้าหนังสือคือเลขพิมพ์บนหน้า จึงเก็บทั้งสองแบบให้ผู้ใช้ตรวจสอบได้

### 26. SBERT cosine, BERTScore และ faithfulness ต่างกันอย่างไร?

SBERT cosineวัดความคล้ายเชิงความหมายของข้อความ BERTScoreจับคู่contextual token embeddingsกับreferenceเพื่อคำนวณP/R/F1 Faithfulnessถามว่าข้ออ้างมีevidenceรองรับหรือไม่ งานนี้semantic faithfulnessเป็นthreshold-based proxyและมีLLM judgeในevaluationเดิม ทั้งหมดไม่ใช่คำตัดสินความถูกต้องสมบูรณ์

### 27. Retrieval F1 .333 และ faithfulness 1.000 ควรตีความอย่างไร?

หนึ่งtargetคืนห้าหัวข้อแล้วเจอtargetจะมีprecision=.2 recall=1 จึงF1=.333 ไม่ใช่answer BERTScore ส่วนproxy1.000หมายถึงผ่านเกณฑ์similarityที่กำหนด ไม่ใช่ทุกคำตอบถูก100% ทั้งการกลับความหมายและปนขั้นตอนยังหลุดได้

### 28. ชุดทดสอบ18ข้อเพียงพอไหม และเปรียบเทียบอย่างยุติธรรมอย่างไร?

เพียงพอเป็นproject validationเบื้องต้น ยังไม่ครอบคลุมOOD/history/concurrency/hard paraphrases Embeddingใช้chunks/labels/settingsเดียวกัน LLMใช้frozencontextsและscorerเดียวกัน ต้องเพิ่มhuman labels/หลายreferenceและuncertainty estimatesก่อนสรุปอันดับทั่วไป โดยlatest rerank6ยังตรวจคำตอบจริงเพิ่มเพียง3ข้อ

### 29. History, Quick Reply และ loading ทำงานอย่างไร?

SQLiteเก็บgrounded answersที่ส่งสำเร็จ4รอบ/24ชั่วโมง แยกผู้ใช้กับห้อง ช่วยresolveหัวข้อคำถามต่อ Quick Replyส่งข้อความที่มีหัวข้อครบเข้าRAG Historyไม่ใช่citation evidence ส่วนloadingเป็นLINE APIเฉพาะหน้าจอแชตส่วนตัวที่เปิดอยู่ ไม่ทำให้LLMเร็วขึ้น

### 30. ระบบพร้อมใช้งานจริงและปลอดภัยแค่ไหน?

เดโม/ใช้งานได้ มีsignature validation,dedup,secretsจาก.envและtests32ข้อผ่าน แต่ยังไม่มีdurable queue/load-security auditเต็มรูปแบบ historyมีข้อมูลส่วนตัวและข้อความผ่านLINE/tunnel จึงไม่ใช่local-onlyทั้งเส้นทาง คู่มือเก่าต้องตรวจข้อมูลปัจจุบัน ควรrotate secretsที่เคยเผยแพร่และทำlatest full evaluationก่อนขยายใช้งาน
